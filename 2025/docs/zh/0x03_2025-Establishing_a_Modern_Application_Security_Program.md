# 建立现代化应用安全计划

OWASP Top Ten 列表是意识文档，旨在让人们关注其所涵盖主题中最关键的风险。它们并非完整列表，而只是一个起点。在此前版本的列表中，我们曾建议将启动应用安全计划作为避免这些风险及其他风险的最佳方式。在本节中，我们将介绍如何启动并构建一个现代化的应用安全计划。

 

如果您已经拥有应用安全计划，请考虑使用 [OWASP SAMM (软件保障成熟度模型)](https://owasp.org/www-project-samm/) 或 DSOMM（DevSecOps 成熟度模型）对其进行成熟度评估。这些成熟度模型全面且详尽，可帮助您确定应重点投入精力以扩展和完善计划的方向。请注意：您无需执行 OWASP SAMM 或 DSOMM 中的所有内容就能做好工作，它们旨在为您提供指导并提供多种选择。它们并非旨在提供难以企及的标准或描述无法负担的计划。它们内容广泛，旨在为您提供许多思路和选择。

 

如果您是从零开始启动计划，或者觉得 OWASP SAMM 或 DSOMM 对您的团队来说“过于复杂”，请参考以下建议。


### 1. 建立基于风险的投资组合方法：

* 从业务角度识别您应用组合的保护需求。这部分应部分由隐私法律以及与所保护数据资产相关的其他法规驱动。

* 建立一套 [常见风险评级模型](https://owasp.org/www-community/OWASP_Risk_Rating_Methodology)，其中包含反映您组织风险承受能力的一致可能性和影响因子。

* 相应地衡量所有应用和 API 并确定其优先级。将结果添加到您的 [配置管理数据库(CMDB)](https://de.wikipedia.org/wiki/Configuration_Management_Database) 中。

* 建立保障指南，以正确定义所需的覆盖范围和严格程度。


### 2. 以坚实基础为支撑：

* 建立一套重点突出的政策和标准，为所有开发团队提供应用安全基线以供遵守。

* 定义一套通用的可重用安全控制措施，以补充这些政策和标准，并为其使用提供设计和开发指导。

* 建立应用安全培训课程，该课程是强制性的，并针对不同的开发角色和主题进行定制。


### 3. 将安全集成到现有流程中：

* 定义安全实施和验证活动，并将其集成到现有的开发和运营流程中。

* 活动包括威胁建模、安全设计和设计审查、安全编码和代码审查、渗透测试以及修复。

* 为主题专家以及开发和项目团队提供支持服务，以确保其成功。

* 审查您当前的系统开发生命周期以及所有软件安全活动、工具、策略和流程，然后将其记录下来。

* 对于新软件，在系统开发生命周期（SDLC）的每个阶段添加一项或多项安全活动。下面我们提供了许多可执行操作的建议。确保在每个新项目或软件计划中执行这些新活动，这样您就能知道每件新软件都将以符合您组织可接受安全态势的方式交付。

* 选择您的活动，以确保最终产品满足您组织可接受的风险水平。

* 对于现有软件（有时称为遗留软件），您需要制定正式的维护计划。请查看下方“运营与变更管理”部分中关于如何维护安全应用的想法。


### 4. 应用安全教育：

* 考虑为您的开发人员启动安全冠军计划或通用安全教育计划（有时称为倡导或安全意识计划），以教授您希望他们了解的所有知识。这将使他们保持最新状态，帮助他们了解如何安全地完成工作，并使您所在工作场所的安全文化更加积极。这通常还能改善团队之间的信任，并带来更愉快的工作关系。OWASP 通过 [OWASP Security Champions Guide](https://securitychampions.owasp.org/) 为您提供支持，该计划正在逐步扩展。

* OWASP 教育项目提供培训材料，帮助教育开发人员了解 Web 应用安全。如需动手学习漏洞知识，请尝试 [OWASP Juice Shop Project](https://owasp.org/www-project-juice-shop/) 或 [OWASP WebGoat](https://owasp.org/www-project-webgoat/)。要了解最新动态，请参加 [OWASP AppSec Conference](https://owasp.org/events/)、[OWASP Conference Training](https://owasp.org/events/) 或本地 [OWASP Chapter](https://owasp.org/chapters/) 会议。


### 5. 提供管理层可见性：

* 使用指标进行管理。根据捕获的指标和分析数据推动改进和资金决策。指标包括对安全实践和活动的遵守情况、引入的漏洞、已修复的漏洞、应用覆盖率、按类型划分的缺陷密度以及实例数量等。

* 分析来自实施和验证活动的数据，以寻找根本原因和漏洞模式，从而推动整个企业的战略性和系统性改进。从错误中学习，并提供积极激励以促进改进。



## 建立并使用可重复的安全流程和标准安全控制

### 需求与资源管理阶段：

* 与业务方收集并协商应用的业务需求，包括所有数据资产在机密性、真实性、完整性和可用性方面的保护需求，以及预期的业务逻辑。

* 编制技术需求，包括功能性和非功能性安全需求。OWASP 建议您使用 [OWASP 应用程序安全验证标准(ASVS)](https://owasp.org/www-project-application-security-verification-standard/) 作为为应用设置安全需求的指南。

* 规划并协商涵盖设计、构建、测试和运营所有方面（包括安全活动）的预算。

* 将安全活动添加到您的项目计划中。

* 在项目启动时以安全代表的身份介绍自己，以便他们知道与谁沟通。


### 招标书（RFP）与合同签订：

* 与内部或外部开发人员协商需求，包括与您的安全计划（例如 SDLC、最佳实践）相关的指南和安全需求。

* 评估所有技术需求的满足情况，包括规划和设计阶段。

* 协商所有技术需求，包括设计、安全和服务级别协议（SLA）。

* 采用模板和检查清单，例如 [OWASP Secure Software Contract Annex](https://owasp.org/www-community/OWASP_Secure_Software_Contract_Annex)。<br>**注意：** *附录适用于美国合同法，因此在使用示例附录前请咨询合格的法律意见。*


### 规划与设计阶段：

* 与开发人员和内部利益相关者（例如安全专家）协商规划和设计。

* 定义适合保护需求和预期威胁级别的安全架构、控制措施、对策和设计审查。这应得到安全专家的支持。

* 与事后为应用和 API 添加安全功能相比，从一开始就设计安全功能要经济得多。OWASP 建议将 [OWASP Cheat Sheets](https://cheatsheetseries.owasp.org/index.html) 和 [OWASP Proactive Controls](https://top10proactive.owasp.org/) 作为如何从一开始就包含安全设计的良好起点。

* 执行威胁建模，请参阅 [OWASP Cheat Sheet: Threat Modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html)。

* 教授您的软件架构师安全设计概念和模式，并要求他们在可能的情况下将其添加到设计中。

* 与您的开发人员一起检查数据流。

* 在您的所有其他用户故事旁边添加安全用户故事。


### 安全开发生命周期：

* 为了改进您的组织在构建应用和 API 时遵循的流程，OWASP 建议使用 [OWASP Software Assurance Maturity Model (SAMM)](https://owasp.org/www-project-samm/)。该模型帮助组织制定并实施针对其面临特定风险的软件安全策略。

* 为您的软件开发人员提供安全编码培训，以及您认为有助于他们创建更健壮、更安全应用的任何其他培训。

* 代码审查，请参阅 [OWASP Cheat Sheet: Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html)。

* 为您的开发人员提供安全工具，然后教他们如何使用，尤其是静态分析、软件组成分析、密钥和 [Infrastructure-as-Code (IaC)](https://cheatsheetseries.owasp.org/cheatsheets/Infrastructure_as_Code_Security_Cheat_Sheet.html) 扫描器。

* 如果可能，为您的开发人员创建护栏（技术保障措施，引导他们做出更安全的选择）。

* 构建强大且可用的安全控制措施很困难。尽可能提供安全默认值，并尽可能创建“铺平道路”（使最简单的方式也成为最安全的方式，成为明显的首选方式）。[OWASP Cheat Sheets](https://cheatsheetseries.owasp.org/index.html) 是开发人员的一个良好起点，许多现代框架现在都附带用于授权、验证、CSRF 防护等的标准且有效的安全控制措施。

* 为您的开发人员提供与安全相关的 IDE 插件，并鼓励他们使用。

* 为他们提供密钥管理工具、许可证以及如何使用它的文档。

* 为他们提供可使用的私有 AI，理想情况下设置一个包含大量有用安全文档的 RAG 服务器、您的团队为获得更好结果而编写的提示词，以及一个调用您组织所选安全工具的 MCP 服务器。教他们如何安全地使用 AI，因为无论您是否喜欢，他们都会使用。


### 建立持续的应用安全测试：

* 测试技术功能以及与 IT 架构的集成，并协调业务测试。

* 从技术和业务角度创建“正常使用”和“滥用”测试用例。

* 根据内部流程、保护需求以及应用假定的威胁级别管理安全测试。

* 提供安全测试工具（模糊测试工具、DAST 等）、安全的测试场所以及如何使用它们的培训，或者为他们进行测试，或者聘请测试人员。

* 如果您需要高保证级别，请考虑进行正式的渗透测试，以及压力测试和性能测试。

* 与您的开发人员合作，帮助他们根据错误报告决定需要修复的内容，并确保他们的经理给他们时间进行修复。


### 发布：

* 将应用投入运营，并在需要时从以前使用的应用迁移。

* 完成所有文档，包括变更管理数据库（CMDB）和安全架构。


### 运营与变更管理：

* 运营必须包括应用安全管理指南（例如补丁管理）。

* 提高用户的安全意识，并管理可用性与安全性之间的冲突。

* 规划和管理变更，例如迁移到应用或其他组件（如操作系统、中间件和库）的新版本。

* 确保所有应用都在您的清单中，并记录所有重要细节。更新所有文档，包括 CMDB 以及安全架构、控制措施和对策中的内容，以及任何运行手册或项目文档。

* 对所有应用执行日志记录、监控和告警。如果缺少，请添加。

* 创建有效且高效的更新和补丁流程。

* 创建定期扫描计划（希望包括动态、静态、密钥、IaC 和软件组成分析）。

* 修复安全错误的 SLA。

* 为员工（理想情况下也包括您的客户）提供报告错误的方式。

* 建立经过培训的事件响应团队，他们了解软件攻击的样子以及可观测性工具。

* 运行阻止或屏蔽工具以阻止自动化攻击。

* 每年（或更频繁地）强化配置。

* 至少每年进行一次渗透测试（取决于您的应用所需的保证级别）。

* 建立用于强化和保护软件供应链的流程和工具。

* 建立并更新业务连续性和灾难恢复计划，其中包含您最重要的应用以及用于维护它们的工具。


### 系统退役：

* 任何需要的数据都应归档。所有其他数据应安全擦除。

* 安全地退役应用，包括删除未使用的帐户、角色和权限。

* 在 CMDB 中将应用的状态设置为“已退役”。


## 将 OWASP Top 10 用作标准

OWASP Top 10 主要是一份意识文档。然而，这并未阻止组织自 2003 年其诞生以来将其用作事实上的行业应用安全标准。如果您想将 OWASP Top 10 用作编码或测试标准，请注意它只是最低要求，并且只是一个起点。

将 OWASP Top 10 用作标准的一个困难在于，我们记录的是应用安全风险，而不一定是易于测试的问题。例如，[A06:2025-Insecure Design](A06_2025-Insecure_Design.md) 超出了大多数测试形式的范围。另一个例子是测试是否实施了适当的、正在使用的、有效的日志记录和监控，这只能通过访谈和请求有效事件响应的样本来完成。静态代码分析工具可以查找日志记录的缺失，但可能无法确定业务逻辑或访问控制是否记录了关键的安全漏洞。渗透测试人员可能只能确定他们在测试环境中触发了事件响应，而测试环境很少像生产环境那样进行监控。

我们鼓励任何希望采用应用安全标准的人使用 [OWASP Application Security Verification Standard](https://owasp.org/www-project-application-security-verification-standard/)（ASVS），因为它设计为可验证和可测试，并且可以在安全开发生命周期的所有部分中使用。

ASVS 是工具供应商唯一可接受的选择。由于 OWASP Top 10 中若干风险的性质（参见 [A06:2025-Insecure Design](A06_2025-Insecure_Design.md)），工具无法全面检测、测试或防御 OWASP Top 10。OWASP 不鼓励任何声称完全覆盖 OWASP Top 10 的说法，因为这根本不真实。
